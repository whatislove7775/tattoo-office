# Tattoo Office · 2.0

Рабочая тестовая версия сайта студии и коворкинга по предоставленным макетам. Оригинальные фотографии, логотипы и канцелярские значки сохранены. Восстановлены исходные оболочка Claude, плавающие портреты, страницы мастеров и интерьера. Геометрия бокового меню, узкие блоки аренды/входа, контрастные XP-подписи и фавикон исправлены по макетам.

## Запуск

Нужен Node.js 22.9+.

```sh
npm ci
cp .env.example .env
# В .env задайте ADMIN_EMAIL и собственный ADMIN_PASSWORD (12–128 символов).
npm start
```

Открыть `http://127.0.0.1:3000`. Админка — `/#/admin`, после входа созданным аккаунтом. Пароля администратора в исходниках нет. ADMIN_* используются только при первом создании аккаунта; смена этих переменных не сбрасывает существующий пароль.

Без `DATABASE_URL` используется локальный PostgreSQL в WebAssembly (PGlite), с сохранением в `work/database`. Это режим разработки, не production-хранилище. С `DATABASE_URL` используется обычный PostgreSQL через `pg`. В production URL БД обязателен.

## Реализовано

- Исходная главная с движущимися портретами; мобильная сетка, контрастные подписи.
- Оригинальные фотографии интерьера и работ. Редактор имён, описаний, стилей и привязки работ мастерам. Исходные демонстрационные карточки сохранены; перед запуском их нужно заполнить данными студии.
- Регистрация резидентов с двумя отдельными согласиями. Гостевые аккаунты создаёт персонал. Пароли scrypt, HttpOnly-сессии, серверная проверка ролей, ограничение частоты запросов.
- Telegram OIDC Authorization Code + PKCE, проверка JWT через JWKS, одноразовый state, привязка к уже вошедшему пользователю. Новому пользователю всё равно нужны email и принятие правил. Требуются Client ID/Secret от BotFather.
- Публичная доступность, 3/6/12 часов, тариф по роли, выбор места, услуги и склад. Проверка пересечений и остатков в одной транзакции.
- Резерв на 15 минут; возврат зарезервированных средств и товаров по истечении времени. Все операции, меняющие доступность, сериализованы блокировкой строки настроек — подход для небольшой студии.
- Предоплата с баланса в первую очередь. Тестовое подтверждение платежа, повторный вызов не удваивает деньги или номер сеанса.
- Ранняя отмена на баланс; поздняя — рассмотрение администратором либо удержание по настроенному правилу. Правила и тарифы сохраняются в самой брони.
- Ручная запись без предоплаты, итоговый счёт, повышение тарифа администратором или мастером, завершение после оплаты.
- Кабинет: активные/прошедшие записи, журнал баланса, входящие уведомления, профиль, смена пароля, цикличная книжка сеансов 1–20.
- Один уровень доступа персонала — администратор с полным управлением сайтом. Резидент и гость — типы аккаунтов мастеров.
- Админка: расписание, места, закрытие интервалов, люди/роли/деактивация/email, склад и услуги, счета, платежи, обращения, публикации, настройки, журнал действий и очередь интеграций.
- CloudPayments checkout и HMAC-обработчики Check/Pay/Fail; адаптер CloudKassir с отдельными документами предоплаты и полного расчёта; Google Calendar по одному календарю на место; адаптеры Email и Telegram; персистентная очередь с повторными попытками и напоминаниями.

## Что работает только как тестовый стенд

Боевой режим **намеренно заблокирован** до проверки документов, размещения в РФ и кассового учёта. Наличие адаптера не означает, что внешний сервис уже подключён. Без ключей тестовые платежи не списывают деньги, документы имеют статус `simulated`, письма/сообщения/события в Google не отправляются. Интерфейс это явно показывает.

Проверка кассы с реальным кабинетом, возвраты на карту, чеки переноса аванса через внутренний баланс, полностью предоплаченные сеансы и сверка неоднозначного ответа провайдера требуют отдельной приёмки до снятия блокировки. Здесь нет заявления о готовности к приёму реальных денег. Список: [docs/LAUNCH.md](docs/LAUNCH.md).

Существующий Telegram-бот не изменён: его код и контракт не предоставлены. API уже общий для веб-интерфейса; интеграция существующего бота описана в [docs/API.md](docs/API.md).

## Развёртывание

Предпочтительно один домен с HTTPS для интерфейса и API, сервер и PostgreSQL в выбранном владельцем дата-центре РФ. `Dockerfile` и `compose.yaml` включены. Перед запуском задайте `POSTGRES_PASSWORD`, `APP_ORIGIN`, `ADMIN_*` в `.env`.

```sh
docker compose up -d --build
```

Порт 3000 опубликован только на loopback; перед ним нужен HTTPS reverse proxy. В production cookie `Secure`. Тестовая кнопка оплаты отключена в production.

Текущий Vercel-сайт не заменён автоматически. Старый статический способ деплоя для этой версии недостаточен: нужен Node API и PostgreSQL. Не сливайте ветку в автодеплой до выбора инфраструктуры. Исходные `js/app.js` и `css/app.css` управляют оболочкой; `js/office.js` подключает API и рабочие формы.

## Проверки

```sh
npm test
npm run check
```

API-тесты запускают чистую PGlite БД. Они проверяют роли, согласия, конкурентную запись, повторный платёж, отмены, склад, истечение резерва, закрытые интервалы, ручную запись, итоговый счёт, тестовые чеки и уведомления. Они не заменяют прогон на production PostgreSQL и кассовой песочнице.

`tests/browser.mjs` — сквозной тест Chrome при работающем локальном сервере. Для теста администратора он читает локальный (игнорируемый Git) файл `work/preview.env` с `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Запуск: `node tests/browser.mjs`. Тест создаёт только тестовые записи и проверяет регистрацию → бронь → оплату → отмену → баланс, админку и мобильное отображение.

## Структура

- `js/office.js`, `css/office.css`, `index.html` — интерфейс.
- `server/index.js` — REST и права.
- `server/schema.sql`, `db.js`, `domain.js`, `reservations.js` — PostgreSQL и бизнес-правила.
- `server/telegram.js` — OAuth.
- `server/worker.js`, `integrations.js` — очередь, напоминания, сервисы.
- `assets/` — оригинальные материалы.
- `tests/` — API и браузерные проверки.

Все суммы хранятся целыми копейками, время — `timestamptz`; интерфейс студии использует Europe/Moscow. Секреты не отправляются браузеру и не коммитятся.
